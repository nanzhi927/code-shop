### 正文（1500-3000 字干货长文，9 段结构）

**一、背景：业务系统选得好，一半的工作量就省下来了**

先说结论：房屋租赁是 Java 管理系统类题目里业务链最完整、答辩友好度很高的方向之一，适合大部分普通水平的同学。

为什么这么说？自己做项目、也陪同学踩过一圈坑之后，我发现大多数管理系统题目的问题不是"难"，而是"薄"——就两三个角色、三五张表，功能罗列完就没东西可讲。房屋租赁不一样，它天然有一条完整的业务链：找房→看房→签约→居住→报修→评价，每个环节都有页面可演示、有表可设计、有逻辑可讲。这篇拿一套我实测跑通的 SpringBoot 房屋租赁系统（管理员/用户/房主三角色，18 张表），从选题到答辩完整过一遍。

**二、选题与选型：为什么这个方向适合**

1. 业务零解释成本。租房这件事人人经历过，答辩页面一放，老师秒懂，不用花时间解释领域概念。
2. 三角色天然分权。管理员（平台治理）、房主（供给侧）、用户（需求侧），权限划分不需要人为编造，RBAC 有真实落点。
3. 数据库密度合适。18 张表，比"5 张表的学生系统"有设计可讲，又不会像 40+ 表那样把自己淹没。
4. 风险提示（诚实说）：业务环节多，别贪多全铺开，抓住"预约→合同→报修"主线讲透即可；拿到任何工程务必先跑通再动笔。

**三、系统功能设计：模块怎么划分**

这套系统一句话：**三角色 + 全流程闭环的租赁平台**。前台 6 栏目：首页、房屋信息（房源列表，字段含月租金/押金/租赁方式/面积/朝向楼层/小区/设施）、我要当房主（用户申请成为房主）、公告信息、留言反馈、个人中心。

后台按角色分三块：
- 管理员 13 组：用户管理、房主管理、房屋类型管理、房屋信息管理、预约看房管理、合同信息管理、房屋报修管理、维修处理管理、房屋评价管理、我要当房主管理（审核）、留言板管理、系统管理（轮播图/公告）、个人中心；
- 用户端 8 项：预约看房、合同信息、房屋报修、维修处理跟踪、房屋评价、我要当房主申请、我的收藏、个人中心；
- 房主端 7 项：管理自己的房源、审核预约、管理合同、处理报修、跟进维修、回复评价、个人中心。

**加分点在业务闭环**：用户预约看房 → 房主/管理员审核 → 生成合同（月租、押金、租用月数、合同金额，带支付状态字段）→ 入住后提交报修（类型细分到水工/电工等）→ 维修处理记录维修进度（维修中/已完成）→ 完成后对房屋评价打分。另外还有一条支线：普通用户可申请"我要当房主"，审核通过后身份升级，可以发布自己的房源——这就是一个现成的"角色权限流转"案例，答辩讲权限设计时非常出彩。

**四、数据库设计：18 张表怎么分类**

库名 springboot08hr3，脚本共 18 张表，拆开很清晰：

- 系统支撑 3 张：config（参数配置）、token（登录令牌）、users（管理员账号）；
- 公告与留言 2 张：news（公告）、messages（留言板）；
- 租赁业务 13 张：房屋信息、房屋类型、房主、用户、预约看房、合同信息、房屋报修、维修处理、房屋评价、我要当房主、房屋信息评论、我要当房主评论、收藏。

关键表以房屋信息为例，字段覆盖：房屋名称、类型、图片、租赁方式、朝向楼层、面积、房屋状态、小区、详细地址、月租金、押金、房屋设施、详情、发布日期、房主账号——一个房源表就把"展示维度 + 交易维度 + 归属维度"都装下了，论文里分析表设计时可以按这三个维度展开，比罗列字段高级得多。

合同表也值得单独讲：合同编号、月租金、租用月数、租用金额、押金、合同金额、合同内容（附件）、生效日、有效期至、支付状态。金额字段齐全，可以顺势引出"金额一致性校验"这类话题。ER 图建议画三层：权限层（用户/房主/管理员与审核关系）、交易层（预约→合同→支付状态）、服务层（报修→维修处理→评价）。

**五、技术实现要点：两个值钱的技术点讲透**

**1. MyBatis-Plus 2.3 做数据访问**。在裸 MyBatis 之上叠了通用 CRUD（selectPage/insert/updateById），单表的增删改查不用手写 SQL，分页用 Page 插件一行搞定；复杂关联查询再回落到 XML 手写。答辩被问"为什么不全部手写 SQL"，答：单表操作交给通用层减少重复代码，复杂查询保留 SQL 可控性——分层使用比全盘照搬更能体现工程判断。

**2. Shiro 1.3.2 做三角色权限**。结构是经典的"账号-角色-功能"映射：管理员、房主、用户登录后走各自的功能菜单；登录态由 token 表 + Shiro 会话管理支撑。加分讲法是结合"我要当房主"业务：申请审核通过后账号角色变化，可见功能随之变化——权限不是静态配置，而是跟着业务状态流转的，这一点比背 RBAC 概念有说服力得多。

顺带两个小点：前台静态页 + 后台 Vue（Element-UI）的混合前端架构，可以聊"为什么后台选 Vue 单页应用而前台用服务端渲染"（后台交互密集适合 SPA，前台内容展示简单直接）；Hutool 工具库处理日期/校验，减少样板代码。

**六、运行与部署：从导库到跑通**

环境：JDK 1.8+、Maven、MySQL 5.7+，Windows/MacOS 均可。

步骤：
1. 建库导脚本：`create database springboot08hr3 default character set utf8;` → `use springboot08hr3;` → `source db.sql;`，导完应看到 18 张表，少表就是没导完；
2. 改 `src/main/resources/application.yml`：数据库用户名密码（默认 root/123456）、端口（默认 8080）；
3. 启动：IDEA 运行主类 `SpringbootSchemaApplication`，或 `mvn spring-boot:run`；
4. 验证：后台访问 `/admin/dist/index.html` 登录（管理员账号 abo/abo），前台访问 `/front/index.html`。

**七、踩坑与经验（真实高频问题）**

1. 数据库连接失败（Access denied / Communications link failure）：九成是 application.yml 里密码/库名没改对，或 MySQL 服务没启动。先命令行 `mysql -u root -p` 验证。
2. 改了后台页面没生效：后台是 Vue 工程，dist 是构建产物，改了 src 下的源码必须重新 build 才能看到变化——这是混合前端架构最常见的困惑。
3. 上传图片显示不出来：图片路径前缀带 context-path（/springboot08hr3/upload/...），用 Nginx 反代或改端口后要整体核对路径。
4. 经验之谈：先跑通再动笔；演示提前彩排"预约→审核→合同→报修→评价"主线，每步切换角色登录，节奏提前排好。

**八、答辩要点：这套系统会被问什么**

- "三个角色的权限怎么划分的"——管理员管平台与审核，房主管自己的房源与租务，用户消费与反馈；结合"我要当房主"的角色流转讲；
- "数据库多少张表、怎么分的"——18 张 = 系统支撑 3 + 公告留言 2 + 业务 13，能说出构成就赢了大部分同学；
- "合同金额和月租×月数对不上怎么办"——答后端生成时计算并落库，支付状态单独维护，展示时以合同表为准（一致性校验思路）；
- "报修流程怎么设计"——报修单与维修处理分离成两张表，报修是需求，维修处理是执行记录（进度、反馈），状态机思路；
- "是你自己写的吗"——千万别说从零手写，诚实答"基于成熟的脚手架结构二次开发，我能讲清每个模块的原理和业务流转"，反而过关。

**九、总结与引导**

房屋租赁方向：业务链完整、三角色分权真实、数据库密度合适，好开题也好答辩，前提是把"预约-合同-报修-评价"主线和 18 张表的构成吃透。我这套实测跑通过；丑话说前面——**论文文档是没有的**（工程包里只有论文截图），只有工程+数据库脚本+运行说明+PPT，论文要自己写。
