### 正文（1500-3000 字干货长文，9 段结构）

**一、背景：业务链路完整的项目，答辩才扛得住追问**

先说结论：在线考试系统是 Java 毕设里业务链路完整、答辩友好度高的方向，适合大部分普通水平的同学。

很多管理类项目的通病是"业务太薄"——增删改查堆一圈，答辩老师问"你这个系统的核心业务逻辑是什么"，答不上来。考试系统不存在这个问题：出题 → 组卷 → 限时答题 → 自动判分 → 成绩与错题，每一环都有真实逻辑。这篇拿一套我实测跑通的 SpringBoot 在线远程考试系统（三角色、12 张表），从选题到答辩完整过一遍，每一段都能直接对照论文目录用。

**二、选题与选型：为什么考试方向适合毕设**

1. 业务零解释成本。谁都考过试，开题讲业务不用铺垫；"在线考试"在远程教学背景下还有现实意义，选题意义那段好写。
2. 技术点密度高。多题型支持、选项的灵活存储、自动判分逻辑、计时考试、三角色权限，每个都能在论文里独立成节。
3. 工作量适中可控。核心业务集中在考试流程上，不像电商那样分支爆炸；12 张表规模合理。
4. 风险提示（诚实说）：判分逻辑看似简单，多选题"全对方算分、部分对怎么算"这类规则要先定清楚，不然代码写着写着会乱。

**三、系统功能设计：模块怎么划分**

这套系统一句话：**管理员/老师/用户（学生）三种角色，前台考试 + 后台管理，同一个 SpringBoot 工程提供接口**。角色划分天然对应论文的权限设计章。

前台 4 栏目：首页（核心内容与功能入口）、试卷列表（可参与的考试）、公告（考试通知）、个人中心（资料与成绩）。

后台按角色分三组：
- 学生端：个人中心、公告查看、考试管理（参与已发布考试）；
- 老师端 5 组：个人中心、公告管理、用户管理（学生维护）、试卷管理、考试管理；
- 管理员端 8 组：个人中心、公告类型管理、公告管理、用户管理、老师管理、试卷管理、考试管理、轮播图信息。

**加分点在考试全流程闭环**：老师在后台维护试题并组卷（设考试时长、总分数、试卷状态）→ 试卷发布后学生前台限时答题 → 系统自动判分、生成带考试编号的考试记录 → 答题详情逐题留存、错题进错题表。这条链路画成流程图就是"系统总体设计"章的核心插图。

**四、数据库设计：12 张表怎么分类、怎么讲**

库名 zaixianyuanchengkaoshixitong，脚本共 12 张表：

- 业务表 7 张：`exampaper`（试卷：名称/考试时长（分钟）/总分数/试卷状态/逻辑删除）、`examquestion`（试题：所属试卷外键/试题名称/选项/分值/正确答案/答案解析/试题类型/排序）、`examrecord`（考试记录：含考试编号、考试用户）、`examredetails`（答题详情）、`examrewrongquestion`（错题表）、`gonggao`（公告）、`laoshi`（老师）；
- 系统表 5 张：`config`（配置/轮播图）、`dictionary`（字典）、`token`（令牌）、`users`（管理员）、`yonghu`（用户）。

两张表的设计值得在论文里展开：

**examquestion 的选项字段**：选项存成 JSON 字符串（如 `[{"text":"答案A","code":"A"},...]`）。为什么不用一列存一个选项？因为单选 4 个选项、多选 4 个、判断 2 个、填空 0 个，选项数量不定——JSON 存储让一张表装下所有题型，扩展新题型也不用改表结构。这是"表结构设计服务于业务扩展性"的现成案例。

**exampaper 的逻辑删除字段**：`exampaper_delete`（0 未删除/1 已删除），删除操作不物理删数据。答辩被问"为什么做逻辑删除"，答：考试数据有审计价值，物理删除不可恢复，逻辑删除保留数据且查询时过滤——一句话讲清设计权衡。

ER 图按"试卷-试题-考试记录-答题详情-错题"这条主链画，加上用户/老师两张角色表，层次一目了然。

**五、技术实现要点：两个值钱的技术点讲透**

**1. 自动判分逻辑**。判分发生在提交答卷时：按考试编号把答题详情落库，客观题（单选/判断）比对正确答案直接得分；多选题按全对才得分的规则处理；填空题比对标准答案。成绩汇总进考试记录，错题同步写错题表。答辩被问"判分在前端还是后端做"，答：必须后端——前端判分可以被绕过，正确答案不能下发到答题页面，后端判分同时确保公平与答案安全，这个回答能体现安全意识。

**2. 三角色权限（Shiro + token）**。管理员/老师/学生三种角色，接口层用自定义 @IgnoreAuth / @LoginUser 注解控制免鉴权与登录态，token 表支撑无状态校验。被问"老师和管理员功能重叠怎么办"，答：同为后台角色，但管理员独有"公告类型管理、老师管理、轮播图"等全局配置能力，老师聚焦"题、卷、考"业务能力——按职责切分权限，这就是 RBAC 的落地。

顺带一个小点：Shiro 1.3.2 + MyBatis-Plus 2.3 的组合是经典脚手架配置，单表 CRUD 与分页由 MyBatis-Plus 承担，复杂查询走 mapper XML，论文技术选型章有现成的话可写。

**六、运行与部署：从导库到跑通**

环境：JDK 1.8+、Maven、MySQL 5.7+，Windows/macOS 均可。

步骤：
1. 建库导脚本：`create database zaixianyuanchengkaoshixitong default character set utf8;` → `use zaixianyuanchengkaoshixitong;` → `source db.sql;`，导完应看到 12 张表（含 2 套示例试卷、8 道示例试题，可直接体验）；
2. 改 `src/main/resources/application.yml`：数据库用户名密码改成你本机的；
3. 启动：运行启动类，或 `mvn spring-boot:run`；
4. 验证：默认端口 8080，**context-path 是 /zaixianyuanchengkaoshixitong**——前台 `/zaixianyuanchengkaoshixitong/front/index.html`，后台 `/zaixianyuanchengkaoshixitong/admin/dist/index.html`。账号：管理员 admin，用户 a1，老师 a1（密码 123456，管理员见说明文档）。

**七、踩坑与经验（真实高频问题）**

1. 地址 404：十有八九没带 context-path，所有地址要带 `/zaixianyuanchengkaoshixitong` 前缀。
2. 数据库连接失败（Access denied）：配置文件里密码是默认值，先改成本机 MySQL 密码，命令行先验证账号可登录。
3. 图片上传报错/不显示：文档明说上传图片放 `src/main/webapp/upload`，且**文件名不能含中文**——这个坑官方文档都特意提醒了。
4. 经验之谈：演示前先把示例试卷点一遍完整流程（开始考试→答题→交卷→看成绩→看错题），计时环节注意别让页面停留太久。

**八、答辩要点：这套系统会被问什么**

- "核心业务流程是什么"——出题组卷（时长/总分/状态）→ 限时答题 → 自动判分 → 成绩记录与错题，画流程图一分钟讲完；
- "数据库多少张表、怎么设计的"——12 张 = 业务 7 + 系统 5，重点讲选项 JSON 存储与逻辑删除两个设计决策；
- "自动判分怎么实现的"——后端判分、多选题规则、错题同步入表，安全与公平两条都能展开；
- "三种角色权限怎么做的"——Shiro + token + 注解鉴权，按职责切分角色能力；
- "是你自己写的吗"——别说从零手写。诚实答"基于通用脚手架二次开发，我做了业务梳理和调试验证，每个模块原理都能讲清"，反而过关。

**九、总结与引导**

考试方向：业务链路完整、技术点密度高、答辩有硬货，前提是把判分逻辑、表结构设计、三角色权限这三个点吃透。我这套实测跑通过；丑话说前面——**这套工程没有演示视频**，只有工程+数据库脚本+运行文档+论文参考文档+PPT+任务书+开题报告+截图，论文等文档仅供参考、论文请独立完成。
